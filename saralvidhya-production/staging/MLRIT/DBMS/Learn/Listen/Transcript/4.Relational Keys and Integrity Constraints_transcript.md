> **Prof. AI / Host**: This is the brief on relational model foundations and integrity constraints. You know, relational databases actually rely on super strict mathematical foundations and integrity invariants to keep massive amounts of enterprise data perfectly structured, connected, and safe from chaotic errors. First, let's map out the mathematical building blocks of tables or relations. A row is a tuple, and a column is an attribute. To picture it simply, arity is the width or number of columns. Cardinality is the height or total rows. And the domain? Well, the domain is basically the bouncer, making sure only the exact right type of data gets into the column.

### `[00:35 - 01:12]` • **Lecture Segment** (115 words)
> **Prof. AI / Host**: Second, we've got the key constraints hierarchy. This narrows down from a broad super key to a minimal candidate key, right down to the specific primary key chosen by the designer. But what happens if a primary key is left blank? Well, thanks to the entity integrity rule, primary keys can never accept null values, because you simply can't track a record that lacks a fundamental identity. Finally, we use referential integrity and foreign keys to link our tables together. But what happens when a referenced parent record is deleted? SQL gives you a few options. Restrict rejects the deletion. Set null leaves the referencing foreign key blank. And set default assigns a fallback value.

### `[01:12 - 01:29]` • **Lecture Segment** (50 words)
> **Prof. AI / Host**: Then there's cascade, which is literally like falling dominoes. If you delete the parent record, all the connected dependent records are automatically wiped out with it. Ultimately, relational databases use precise mathematical dimensions and rigid key constraints to ensure every piece of your data stays flawlessly accurate and perfectly linked.
